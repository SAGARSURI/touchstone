# Phase 3 step 5: A10 and budgets, results

Run on 2026-10-09 on Linux x64 (the project container, 4 CPUs), Flutter
3.47.6, with `test/a10/a10_test.dart`. Scored against
[a10_expectations.md](a10_expectations.md) as written. Raw data in
[a10/](a10/): the wall times, and per-scene stopwatch times for each run.

One change from the written method: the 1,000-round comparison timings run
in a fourth mode, `compare`, so they are not part of the `capture` wall
time. Run 1 of each mode includes compiling the test and is left out of the
medians.

## Budgets

| Budget | Result | Met |
| --- | --- | --- |
| Capture adds under 20% to test time | Wall time of the 41 catalogue tests: 9.6 s without capture, 14.2 s with it (medians of runs 2 and 3: 9.0 and 9.6 s; 13.4 and 14.2 s). **+48%** | **no** |
| A hash-equal comparison takes under 1 ms per snapshot | Comparing root hashes and toolchains: 1.2 to 12.5 µs per snapshot. With the baseline's parse included: 0.2 to 2.5 ms; over 1 ms on 7 of 41 snapshots (`watchlist/top` 2.5 ms, `watchlist/scrolled` 2.4 ms, `settings/default` and three settings matrix scenes 1.15 to 1.3 ms, `order/symbol` 1.1 ms) | comparison **yes**; with the parse **no** |

The parse checks every node's hash against the file, which is what makes a
large snapshot slow to read.

## Where the time goes

Summed over the 41 scenes, the pump takes 5.1 s and the capture and
comparison 4.2 s, so capture costs about 82% of the pump. The most expensive
captures are the scenes with nodes that are rasterized:

| Scene | Pump (ms) | Capture and compare (ms) | Opaque reason |
| --- | ---: | ---: | --- |
| `buttons/all` | 555 | 343 | path ×4 |
| `map/default` | 44 | 240 | path, platform view |
| `states/loading` | 42 | 233 | unknown shader |
| `live/initial` | 52 | 180 | path ×8 |
| `live/flashing` | 50 | 173 | path ×8 |

Scenes with no rasterized node cost 24 to 82 ms. This is inferred from the
per-scene times, not profiled.

The share counts components, not render objects: a component is opaque when
any render object it owns needs pixels. Most of the catalogue's components
contain a Material button or field, whose shape is a path.

## What the spec allows

The spec says an over-budget result is met by adding shards or renegotiating
the budget, never by reducing coverage. A third option that keeps coverage
is to make capture cheaper, for example by rasterizing all of a snapshot's
isolated nodes in one image instead of one image each, and by checking node
hashes lazily when a baseline is parsed. Which one to take is Sagar's call.

# Second measurement, after making capture cheaper

Sagar was asked on 2026-10-09 how to handle the over-budget result, with
"make it cheaper" recommended; this was done while the question was open and
is recorded here either way. Same method, same machine, raw data in
[a10_run2/](a10_run2/).

## What changed

A profile of the 41 captures (stopwatches around each step, not committed)
put 1.5 s in hashing pixels, 1.2 s in building the nodes, of which 0.95 s was
describing `style`, and 0.3 s in recording paint. In hashing pixels, SHA-256
over 21 million pixels took 0.96 s; rasterizing them took 0.2 s.

1. **Pixel digest.** Pixels are hashed with a 128-bit digest written for
   this ([schema_v1.md](../schema_v1.md), "pixels"), not SHA-256. Detection
   is unchanged: any change to a pixel changes the digest. The pixel hashes in
   the baselines change, so the macOS baselines are recorded again.
2. **Explanation only when needed.** `expectSnapshot` checks an unchanged
   snapshot from a capture without `style` and `shape`, which are not hashed,
   and captures again with them only when the hashes differ. The detection
   fields and the change report are the same as before.

Making the baseline's parse lazy was tried and dropped: reading only the
header passed a baseline whose nodes could not be read, which an existing
test rejects.

## Budgets, second measurement

| Budget | Result | Met |
| --- | --- | --- |
| Capture adds under 20% to test time | 9.5 s without capture, 11.0 s with it (medians of three runs; runs 2 and 3: 9.5 and 9.3 s; 10.7 and 11.1 s). **+16%** | **yes**, on this machine |
| A hash-equal comparison takes under 1 ms per snapshot | Unchanged: the comparison takes microseconds; with the parse, over 1 ms on the same 7 snapshots | comparison yes; with the parse no |

Summed over the scenes, capture and comparison went from 4.2 s to 1.9 s
against 5.2 s of pumping. `buttons/all` is still the most expensive at 238
ms, then `sign_in/focused` at 113 ms.

The margin is small and this is one Linux container. The macOS runners,
where baselines are checked, are not measured here.
